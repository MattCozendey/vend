## Redesign (decided, not built)

A walk over history is replaced by fixed-key reads of replicated facts, so the cost of a write, read and sync does not grow with history (sync costs what differs). Every choice is judged only by the goal: strong, proven, fast, anywhere, eventually consistent, high throughput, graph based with groups, nested semantic data. Proof work is not a cost.

- Heights are 32-bit, high bit first. A line is a list of owner epochs (genesis cells); a step is the majority of the epoch's owners in its bucket; `where(i)` says where a request was decided.
- Strict finality: a sync only appends to a listing (prefix-closed, as `chain_kept` today), not per-step only.
- Versions are persistent trees in the ledger, from resource name to content. Each vote names the tree root it makes, and the next tree is a proven function of the tip tree and the request: a decided step fixes its tree, and any node can recheck it.
- Split votes: vote rounds, so a line with many owners does not stall on a split.
- Owner epochs: each read checks the whole epoch chain back (no weaker one-level check).
- Effects live in transport/IO, one adapter per resource type (file://, a server, any URI kind): each detects changes, retries and optimises in its own way (README). The core stays pure: it sees a resource only as a name (space:path) and bytes.
- Resource contents (bytes, whatever type the resource is) stored once by a hash; a collision shows as a conflict (many), never as wrong content.
- The ledger stays generic in the change type; equality is a structural is_eq per type, proven equal to code equality.
- Scope is not reduced: item-level formats for Bend and C are in scope, with everything else in README.md.
- First: experiments E1-E6 in scratch (32-bit descent and range scan; quorum over a list read once; tree get_set; flat write benchmark at 1k and 10k; visited-set reach transitivity; delta sync law), then the migration in order, each step checking.

A tree is named by its root, a `Maybe<Hash>` (none: the empty tree), as each part of a branch is. Nodes are codes: leaf `[1, key, value]` (lengths first, `Code.words`), branch `[2, parts]` (each a hash or none, no empty part at the end: `Parts.put` trims); `[0]` is the empty node, what an empty part reads as, never stored. One code per node: a read refuses any other code (tags other than 0/1/2, count and value tags other than 0/1, a branch with an empty last part), and `Node.words_of` proves the node read from some words has those words (read-then-write laws `Code.Back` in code.bend for tokens, counts, values, items, lists, words; and for hashes, parts, nodes). `Tree.get` descends by nibbles (`Tree.get.go`, structural, no fuel). `Tree.set` gives the new subtree (`Put`: root and new nodes; the caller puts them as data), or none when the store does not hold a node on the key's path or the key's whole path is another key's (a SHA-256 collision): a write never drops a subtree. A split puts the old part's own reference into the new branch. Laws: `Node.of_words` (decode after code, for a node in its one code: `Node.ok`); `Node.words_of` (code after decode); `Tree.get_set` (after a set, the key reads as its new value in any store that holds the new nodes: `Tree.holds`, a Bool); `Tree.get_other` (another key reads as before, in a store that grows from the old one and holds the new nodes); `Tree.get_grows` (a read stays as the store grows); `Tree.set_some` (a set fails only on a missing node or a collision: `Tree.set.ok`). `Tree.list` lists the bindings of a tree (it walks every node, as deep as a read goes, and lists a leaf only where its key's path leads); `Tree.list_complete` (a binding that reads is listed) and `Tree.list_sound` (a listed binding reads): a key is listed exactly when it reads. Growth is a template pair (`~grows`, `~kept: Tree.Keeps`), which the ledger's `State.grows` and `State.data_grows` fill. Ledger v2's `Vote.result` is the root, a `Maybe<Hash>`. Order-free (proven): `Canon.root` builds a root from a list of distinct bindings alone (a leaf for one, else a branch whose part for each nibble is the canonical root of the bindings under it; its parts are `Parts.put`s, so the laws that puts of other parts commute and a second put replaces the first carry it). `Tree.set_canon`: a write into the canonical tree of bindings bs, in a store that holds it (`Canon.holds.of`, true of the empty tree), gives `Canon.of(Binds.put(bs, k, v))`; `Tree.set_canon_holds`: a store that grows and holds the new nodes holds the new canonical tree, so writes chain; `Tree.set_comm`: writes of two other keys, in either order, give the same root; `Tree.set_twice`: a second write of a key gives the root of that write alone. Measured (native, 1,000 / 10,000 set+get): about 0.6s / 9.5s (noisy machine); 64 nibble conversions per path cost about 4%.

## Design (ledger + core)

- A ledger holds requests, votes and data in one trie of cells; a sync is a join (State.join_comm, join_assoc, join_idem, missing_join).
- A line is epochs of steps its owners decided; each step takes a request or refuses it as stale; an epoch ends after its first owner change. A verdict carries the new tree nodes, which the ledger puts under their hashes before the vote.
- A store is a root chain (Ask.start); its owners make its branches and groups (Change.make), so a name is made once.
- Each version has one Merkle tree (`daemon/shared/tree.bend`) of its line's state; a version's root is its vote's result.
- Laws: ledger: decide_grows, decided_grows, status_grows, refused_kept (finality), ask_grows, ask_holds, ask_decides, ask_decided, ask_data, data_hash, data_grows, put_data_get, vote_grows, Line.steps_grow (a listing only grows at its end). Tree: get_set, get_grows, get_other, set_some, list_complete, list_sound, set_canon, set_canon_holds, set_comm, set_twice. Core: Node.write_written. Every other read (content, merge, conflict, groups, affects, impact, notices) is a def in `core/spec.bend`.

## Decisions taken in this pass

- A creation race cannot replace a chain: creations are decided on the store's chain.
- Stale and Refused are final: owners vote a verdict, once.
- set-owner takes the nodes of a group as it is when the request is made: the owners of the next step must come from the line's own past, or two majorities could disagree.
- Defs in the spec are the spec; laws that restated a def are gone (bend2 skill, Laws that matter).
- Two requests are the same exactly when their codes are; the round-trip proofs in `core/impl.bend` follow one pattern per field.
